## 2. Technical Context & Key Decisions (การตัดสินใจเชิงเทคนิค)
* **Per-transfer `.part` isolation (`df068a3`):** `StreamingFileReceiver` accepts optional `transferId`, appending a 12-hex-char SHA-256 prefix `.${sha256(transferId).substring(0, 12)}.part` so untrusted `transfer_id` values never enter filesystem paths directly; `FileTransfers` passes `transferId: tid` and `MobileNode` allocates one `StreamingFileReceiver` per `_Incoming`.
* **Serialized rename critical section (`53239a7`):** Because `freeNameFor` awaits async `exists()`, two concurrent same-name transfers finalizing at once could both pick `photo.jpg` and either overwrite each other (POSIX) or fail `rename` (`PathExistsException` on Windows). Added `_finalizeLocks` / `_serializeRename` keyed by normalized case-insensitive target path (`wanted.absolute.path`) with `unawaited(guard.whenComplete(...))` cleanup so chunk writes & SHA-256 hashing stay concurrent while `create + freeNameFor + rename` executes mutually exclusively.
* **Dead `.part` resume test repaired (`53239a7`):** In `apps/desktop/test/file_transfer_test.dart`, the pre-existing `resuming from an existing .part` test seeded `Downloads/resume.bin.part`, which no longer matched `FileTransfers`'s `transferId`-scoped `.part` file. Updated the test to seed `StreamingFileReceiver(destinationRoot: dl, transferId: tid).partFileFor(item)` and assert `GET /api/v1/file/$tid/i0/status` returns `offset == kStreamingChunkSize` and truncates the extra 50 B before completing.
