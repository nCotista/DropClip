## iOS Share Extension follow-up (2026-11-06)

- Added a separate stacked branch `spike/S0.2-ios-share-extension` (`b36f19f`, draft PR #52) with a native host and Share Extension Xcode project, sparse 4 GiB test file, App Group staging, file-backed background upload, `getrusage` peak RSS report, and a TLS 1.3 LAN receiver that verifies byte count and SHA-256. This branch is 390 added lines, stacked on the original S0.2 PR #51 to keep each PR below 400 lines.
- Host and extension compile and install on an iPhone 16 Pro simulator. The simulator registers `group.com.dropclip.shared`; its host created a sparse file with logical size 4,294,967,296 bytes and zero allocated data blocks. Host checks pass with 92.31% line coverage; the receiver's happy path and four error cases pass. The host also requires 16 GiB free before starting the real transfer.
- Mac-only loopback verification: a separate Python client streamed the full 4,294,967,296-byte sparse fixture in 1 MiB reads over certificate-verified TLS 1.3 to `receiver.py`. The receiver returned HTTP 200, `valid=True`, and SHA-256 `8479e43911dc45e89f934fe48d01297e16f51d17aa561d4d1c216b1ae0fcddca`. This validates the receiver and wire volume, not the iOS extension or device RAM. The disposable TLS key/certificate and file were removed after the check.
- `xcodebuild build` and `xcodebuild analyze` for the iOS Simulator complete with no diagnostics after Debug build settings were corrected (`7f5c26d`). Device signing and the on-iPhone transfer remain the only iOS acceptance gap.
- Physical iPhone build fails for both target IDs: their current provisioning profiles do not authorize `com.apple.security.application-groups = group.com.dropclip.shared`. A disposable group ID fails with the same mismatch under the available signing team. The iPhone 4 GiB transfer and <30 MiB peak RSS criterion remain unmeasured. Both App IDs need profiles with the shared App Group entitlement before device testing.
